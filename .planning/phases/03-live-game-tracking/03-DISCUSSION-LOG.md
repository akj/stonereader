## Global Hotkey Design

### Q1: Scope of global hotkeys vs in-app Live Game panel

| Option | Description | Selected |
|--------|-------------|----------|
| Mirror: every query has both | Every query (deck, opponent played, mana) answerable via BOTH a global hotkey AND in-app keys when panel is open. Most flexible; more hotkeys to register. | |
| Hybrid + shared modifier prefix | Top queries get global hotkeys via shared `Ctrl+Shift+<letter>` modifier-namespace; deep inspection in the in-app Live Game panel. | ✓ (after layered-keystrokes pivot) |
| Dynamic leader (true Vim-style) | One leader chord re-registers single-key hotkeys for ~2s. More complex; race conditions; possible NVDA/JAWS quirks. | |
| Brief focus theft leader | Leader chord briefly steals focus to capture next key, returns focus. Risky for SR users — focus changes get announced. | |

**User's first response:** "I'm most interested in 2 but want to offer another framework: layered keystrokes. You first press an activation keystroke, then the second key press is routed to the app. thoughts?"

**Notes:** User initially proposed Vim-style leader keys. Claude explained the OS focus constraint with `wx.Frame.RegisterHotKey` (Windows routes the registered chord to the app, but subsequent keys go to whoever has focus — Hearthstone). True leader keys would require focus theft (jarring for SR users), dynamic re-registration (race conditions, complex), or a low-level keyboard hook (conflicts with NVDA/JAWS). User accepted: shared `Ctrl+Shift+<letter>` modifier-namespace IS the leader pattern in disguise — without any of the costs.

### Q2: Which v1 hotkey query gaps to cover

| Option | Description | Selected |
|--------|-------------|----------|
| Status snapshot (4 hotkeys) | D=deck counts, M=mana, O=opponent last play, H=hand counts | Originally recommended; rejected by user |
| Per-fact granular (~7-8 hotkeys) | One hotkey per fact (player deck, opp deck, player mana, ...) | |
| Status snapshot + drill-downs | 4 status + 3 drill-down (opp played list, remaining list, drawn list) | |

**User's response:** "few things. for 3, that longer info should be put into a browseable popout view not just spoken. Hearthstone Access already gives info about your deck, your and the opponent's mana, and a full replay list. I want the things that are not covered by Hearthstone Access keystrokes"

**Critical scope reframe:** Hearthstone Access (HA) already covers own-hand info, mana for both players, board state, and recent-action replay. Phase 3 should target ONLY the gaps. Re-asked with HA-aware options:

| Option | Description | Selected |
|--------|-------------|----------|
| Remaining deck composition | Cards still in your deck with counts (HA shows full deck list but doesn't track drawn). Browse-open: opens panel zoomed to remaining-deck zone. | ✓ |
| Full opponent-played history | Every card opponent has played, in order, with turns. Browse-open: opens panel. | ✗ (user only chose remaining deck explicitly) |
| Cards drawn this game | Chronological list of cards you drew with turn numbers. | ✗ |
| Auto-detected deck identity | Speaks the matched saved deck name. | ✗ |

**User's notes:** "I'd rather see cards still in the deck rather than cards already drawn. also perhaps info about guesses about the opponent's hand- how do other trackers convey that info? would be nice to have an equivalent here: discovered cards, played from which hand position, things like that?"

**New gap surfaced:** Opponent hand inspection added as a second browse-open hotkey target.

### Q3: Opponent hand detail level in v1

| Option | Description | Selected |
|--------|-------------|----------|
| Position + identity (or `?`) + drawn turn | Uses fields Phase 2 already captures. No engine extension. ~70% of HDT. | |

| Above + Discover-in-progress | Adds 'opponent is choosing 1 of 3'. Requires hooking BlockType.PLAY on Discover. Most surface area. | |

### Q4: Continue or move on

**User chose:** Move to next area — leaving exact letter assignments, conflict policy, and diminishing-verbosity to planner discretion.

## Live Game Panel Structure

### Q1: Which zones does the Live Game panel expose?

| Option | Description | Selected |
|--------|-------------|----------|
| Remaining deck | Cards still in your deck with copy counts. | ✓ |
| Opponent hand | Each card opponent is holding: position, identity (or '?'), drawn turn, creation lineage. | ✓ |
| Opponent played history | Every card opponent has played, in order, with turn numbers. | ✓ |
| Game status summary | Read-only top zone: matchup, current turn, detected deck, game type/format. | ✗ |

**User's notes:** "My vision was a hotkey opening a rendered html interface that would be visible and browseable. We could do what you describe, but that sounds more like a panel for the app itself rather than a popped out panel. maybe that makes the design too scattershot though. thoughts? I like 1-3 as info, with perhaps the title giving x (class) vs y (class)."

Status info ("Mage vs Warrior", detected deck name) goes in the panel TITLE bar, not as its own zone.

### Q2: Browse-open UI surface

| Option | Description | Selected |
|--------|-------------|----------|
| Existing Live Game panel in main window | Browse-open hotkey calls `nav.show_panel('Live Game')` + jumps cursor to targeted zone. Same surface reachable two ways. | ✓ |
| Separate floating popup window (`wx.MiniFrame`) | Distinctive popup feel; same SR semantics as option 1; second wx widget surface to maintain. | |
| HTML / WebView popup | Visually distinctive; for NVDA users it's a context switch between app SR mode and browser SR mode; significant new architecture for zero SR benefit. | |

**Notes:** Claude pushed back on the HTML popup framing — for NVDA users, "rendered HTML" and "wxPython window" are functionally identical (both navigated by SR speech of semantic content). The "scattershot" worry is real but solved by recognizing two query types (speak-only + browse-open) sharing one panel surface, not by introducing a second UI surface.

### Q3: Update behavior during a live game

| Option | Description | Selected |
|--------|-------------|----------|
| Live-update + cursor preservation | Re-render on relevant GameEvents; cursor stays on same logical card; quiet during arrow-read. | ✓ |
| Snapshot on entry, manual refresh | Read GameState once when opened; user presses 'r' to refresh. | |
| Live-update with announcement | Re-render AND announce ('Opponent played Fireball'). Risky — could fight NVDA's arrow-read. | |

### Q4: Game lifecycle behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Auto-reset on GameStarted; preserve last game on GameEnded | New game = clean slate. Last game stays visible after end for review. | ✓ |
| Auto-reset on both | Cleaner state; loses post-game review. | |
| Persist across games until manual clear | Risk of confusing data between games. | |

### Q5: Lifecycle speech / auto-open behavior

| Option | Description | Selected |
|--------|-------------|----------|
| Speak, never auto-open | Speak matchup at GameStarted; speak result at GameEnded; no panel auto-open. | |
| Speak + auto-open at game start only | Speak matchup AND open panel (focus shifts to StoneReader). | |
| Silent on lifecycle | NO speech at GameStarted/GameEnded; user explicitly queries via hotkey or opens panel. Most non-invasive. | ✓ |
| User-configurable | Settings flags. Adds settings surface. | |

## Auto-Deck-Detection (LIVE-08)

### Q1: When does detection fire

| Option | Description | Selected |
|--------|-------------|----------|
| After full deck list received | Match against the full 30-card deck list revealed at game start. Most reliable. | ✓ |
| After mulligan resolves (MulliganDone) | Match against 3-4 mulligan-keep cards. Less reliable; fires later. | |
| Both: try after deck list; fall back to mulligan | Belt-and-suspenders for an unlikely edge case. | |

**User's notes:** "research how other deck trackers handle this, but 1 seems like the right way to go"

**Research performed:**
- WebSearch: HDT auto-detect — confirms "tracker tries to automatically select the deck you are playing"
- WebSearch: Firestone — confirms "deck tracker that shows the player's remaining cards"
- `docs/superpowers/research/2026-04-08-powerlog-parsing.md` line 35: hslog ships `FriendlyPlayerExporter`
- HearthSim Hearthstone-Deck-Tracker (https://github.com/hearthsim/hearthstone-deck-tracker)
- Zero-to-Heroes/firestone (https://github.com/Zero-to-Heroes/firestone)

Both trackers use the CREATE_GAME deck list (Phase 2 already exposes as `GameState.player_deck`). Option 1 confirmed.

### Q2: Match policy

| Option | Description | Selected |
|--------|-------------|----------|
| Strict: one exact match wins; otherwise no match | Exact multiset comparison. 0 or 2+ → "no match". Honest about uncertainty. | ✓ |
| Strict + last-played tiebreaker | Same; on multiple matches, pick most recently played. Requires `last_played` timestamp. | |
| Best-fit (highest card overlap) | Match even if not exact. Risk of silent mis-attribution. | |

### Q3: Detection persistence

| Option | Description | Selected |
|--------|-------------|----------|
| Detect once per GameStarted; persist for the game | Cached on LiveGamePresenter; resets on next GameStarted. | ✓ |
| Re-detect on every GameState change | Wasteful; result shouldn't change after CREATE_GAME. | |
| Detect on first query (lazy) | Result computed mid-game when player_deck might already have draws subtracted. | |

### Q4: Detection effect on Remaining Deck zone

| Option | Description | Selected |
|--------|-------------|----------|
| Use revealed deck list either way | Always use in-game player_deck for "remaining" calc. Detected name is just title metadata. Works for unsaved decks. | ✓ |
| Use saved deck composition when matched | Alternate code path; rarely behaves differently. | |
| Skip remaining-deck zone entirely if no match | Loses unsaved-deck use case. | |

### Q5: Continue or move on

**User chose:** Move to Speech format. Game-history persistence (Phase 2 D-15 deferred) explicitly stays deferred to a later phase.

## Speech Format for Queries

| Option | Description | Selected |
|--------|-------------|----------|

| Name + cost + count | '6 mana, Reno Jackson, 1 copy'. More verbose. | |
| Name only; count and cost in detail | Matches existing CardBrowser pattern but less useful at-a-listen. | |

### Q2: Per-row format for Opponent Hand and Opponent Played zones

| Option | Description | Selected |
|--------|-------------|----------|
| Compact contextual | Opp Hand: 'Position 3, Reno Jackson, drawn turn 5' / 'Position 3, unknown, generated by Wand turn 5'. Opp Played: 'Turn 6, Reno Jackson'. | ✓ |
