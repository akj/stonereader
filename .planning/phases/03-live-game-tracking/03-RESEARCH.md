# Phase 3: Live Game Tracking - Research

**Researched:** 2026-04-26
**Domain:** Live game state announcements via global hotkeys + in-app navigable panel; engine extensions for friendly-player resolution and creation lineage tracking.
**Confidence:** HIGH (most claims verified against installed `hslog 1.18.0`, `wxPython 4.2.5`, official Win32 docs, and the captured Power.log fixtures from Phase 2 D-17).

## Summary

Phase 3 wires Phase 2's headless `GameTracker` (subscriber bus, frozen `GameState`, 11 typed events) to two user surfaces: a navigable `LiveGamePanel` with three zones (Remaining Deck, Opponent Hand, Opponent Played History) and a small set of `Ctrl+Shift+<letter>` global hotkeys registered via `wx.Window.RegisterHotKey` / `EVT_HOTKEY` that work while Hearthstone has focus. Two engine extensions are required: (1) `FriendlyPlayerExporter`-driven resolution of the local player (fixes WR-02), and (2) creation-lineage bookkeeping that links opponent-hand `FullEntityPacket`s to their generating `BlockStartPacket` subject card.

All foundational code already exists. `GameTracker.subscribe` synchronously delivers `(event, current_state)` tuples on the GUI thread (Phase 2 D-02), `ZoneNavigationMixin` provides cursor-per-zone navigation with detail inspection (D-13/D-14/D-15), `NavigationController.show_panel` registers panel-swap navigation with focus restoration via `wx.CallAfter`, `SpeechService.speak(text, interrupt: bool)` already supports the speech-queue interrupt model the speak-only hotkeys need, and the captured Power.log fixtures (`tests/fixtures/log/*.log`) round-trip through `Parser+GameEngine` for end-to-end tests.

**Primary recommendation:** Implement Phase 3 in five layers — (1) engine extension for `friendly_player_id` via `FriendlyPlayerExporter` and lineage tracking via `_block_subjects` stack already maintained by the engine, (2) `LiveGamePresenter` subclassing `ZoneNavigationMixin` with three zones and a `tracker.subscribe` callback, (3) `LiveGamePanel` passive view, (4) `services/_global_hotkey.py` thin wrapper around `wx.Frame.RegisterHotKey`/`UnregisterHotKey`/`EVT_HOTKEY` with conflict-aware registration, (5) `MainWindow.OnInit` wiring + `MENU_ITEMS` extension. No new external dependencies.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Global Hotkeys (LIVE-09)**
- **D-01:** Hybrid model with shared-modifier namespace — small set of global chords using the same `Ctrl+Shift+<letter>` modifier prefix (the de facto leader namespace). True Vim-style leader keys are rejected — under Windows `RegisterHotKey`, the OS routes only the specific registered chord; subsequent keys go to whoever has focus (Hearthstone). Sharing a modifier prefix gives the same mental "leader" feel without focus theft, dynamic re-registration races, or low-level keyboard hooks that conflict with NVDA/JAWS.
- **D-02:** Hotkey query gaps targeted in v1: (1) Remaining deck composition (browse-open: hotkey opens the Live Game panel zoomed to the remaining-deck zone). (2) Opponent hand inspection (browse-open: opens panel zoomed to opponent-hand zone). HA already handles own-hand, both-mana, board, recent-replay — these get no v1 hotkey.
- **D-03:** Two query types: speak-only and browse-open.
  - Browse-open (always opens the Live Game panel + jumps cursor to a target zone): Remaining Deck panel, Opponent Hand panel.
  - Speak-only (just announces via SpeechService; no UI surface change): exact list deferred to planner — likely candidates include LIVE-06 deck-count comparison ("18 left, opponent 22"). Format is locked (D-12) so any added hotkey speaks consistently.
- **D-04:** Opponent hand v1 detail level: position + identity (or `?`) + drawn turn + creation lineage. Lineage = "generated by Cabal Shadow Priest" / "discovered from Wand of Disintegration". Requires Phase 3 engine extension to link `FullEntityPacket` to its creating `BlockStartPacket` (engine bookkeeping pass). Discover-in-progress signal (mid-Discover state) deferred to v2.

**Live Game Panel Structure**
- **D-05:** Three zones in the Live Game panel: (1) Remaining Deck, (2) Opponent Hand, (3) Opponent Played History. Each zone uses `ZoneNavigationMixin` with cursor + N-of-M speech + down-arrow detail inspection. NO separate "status" zone — matchup ("Mage vs Warrior") and detected deck name go in the panel title bar.
- **D-06:** One UI surface, two ways in. The Live Game panel is reachable from the home menu (add `"Live Game"` to `MENU_ITEMS` in `presenters/home.py`) AND directly via global hotkeys (browse-open hotkey calls `nav.show_panel("Live Game")` then jumps cursor to the targeted zone). HTML/WebView popup explicitly rejected.
- **D-07:** Live-update on relevant `GameEvent` subscriptions, with cursor preservation. Panel re-renders when Phase 2 events affect a visible zone. Cursor stays on the same logical card if possible (e.g., "Reno Jackson" stays selected even if list reorders). Updates are silent during arrow-read (no announcement) — user explicitly arrows to hear changes.
- **D-08:** Lifecycle: Auto-reset on `GameStarted`. Preserve last game on `GameEnded` (post-game review). New `GameStarted` overwrites the preserved state. When no game has been seen this session: panel shows "No game in progress" across all zones.
- **D-09:** Silent on lifecycle. No speech at `GameStarted` or `GameEnded`. No automatic panel-open on `GameStarted`. User explicitly queries via global hotkey or opens the panel via home menu.

**Auto-Deck-Detection (LIVE-08)**
- **D-10:** Detect once per game using the full revealed deck list. Detection fires after the engine has fully consumed `CreateGamePacket` and `GameState.player_deck` is populated with the 30 cards Hearthstone reveals to the local player at game start. Result is cached on the `LiveGamePresenter` for the duration of the game; subsequent panel queries / hotkeys see the same detected deck. Re-runs on next `GameStarted`.
- **D-11:** Strict exact match: one match wins, otherwise no match. Compute multiset of `(card_id, count)` over the 30 revealed cards. For each saved deck in the SQLite `decks` table, compare to its multiset. If exactly one saved deck matches exactly → that's the detected deck (panel title shows its name). If 0 or 2+ match → "Unknown deck" in the panel title.
- **D-12:** Remaining-deck calculation always uses the in-game `player_deck` (revealed by Hearthstone via `CREATE_GAME` and decremented on draw events), regardless of detection result. The detected saved deck name is only metadata for the panel title.

**Speech Format**
- **D-13:** Per-row format for Remaining Deck zone: `"Reno Jackson, 1 copy"` / `"Fireball, 2 copies"`. Sorted by mana cost ascending then alphabetically. Cards drawn-to-zero stay listed as `"0 copies"` so user can confirm they came out. Down-arrow reveals card text via `Card.detail_lines()`.
- **D-14:** Per-row format for Opponent Hand zone (compact contextual): `"Position 3, Reno Jackson, drawn turn 5"` (revealed) or `"Position 3, unknown, generated by Wand turn 5"` (lineage known) or `"Position 3, unknown, drawn turn 5"` (no lineage). Down-arrow reveals card text + full lineage chain.
- **D-15:** Per-row format for Opponent Played zone: `"Turn 6, Reno Jackson"`. Chronological. Down-arrow reveals card text.
- **D-16:** Speak-only global hotkey format (single-fact, while Hearthstone has focus): tight one-sentence. Examples: `"18 left, opponent 22."` / `"Opponent has Reno Jackson, drawn turn 5, generated by Wand."`.
- **D-17:** Panel-entry / hotkey-jump speech: `"Remaining deck zone, 18 of 18 cards. 1 mana, Glacial Shard, 1 copy."` Format = zone name + count + first-row read.

**WR-02 — Friendly Player Resolution**
- **D-18:** Use hslog's `FriendlyPlayerExporter` to resolve the local player per-game. Wire it into the engine's CREATE_GAME flow so `_friendly_player_id` is set correctly each game. Zero new dependencies. Replaces the stub at `stonereader/services/_engine.py` line ~85. New tests cover both Player-1-is-local and Player-2-is-local cases.

**Engine Extensions Required by Phase 3**
- **D-19:** Engine extension 1 — creation lineage tracking. When a `BlockStartPacket` opens a `POWER` block whose subject is a known card, and a `FullEntityPacket` arrives inside that block whose entity ends up in the opponent's hand, record `(opponent_entity_id → "generated by <subject_card_name>")` on the entity. Stored in `GameEntity.tags` or as a new optional field — planner picks. Discover-in-progress (mid-block) NOT tracked in v1.
- **D-20:** Engine extension 2 — sorted remaining-deck view. Phase 2 D-08 already gives `player_deck: Tuple[GameEntity, ...]`. Phase 3 needs either (a) a derived computed property on `GameState` that returns sorted-by-cost-then-name `(Card, count)` tuples, OR (b) presenter-side sorting/grouping. Planner's call.

### Pattern 1: Friendly Player Resolution via FriendlyPlayerExporter (D-18)

**What:** Replace the `_friendly_player_id = 1` stub at `_engine.py:85` with an algorithm derived from `hslog.export.FriendlyPlayerExporter`. The engine doesn't import hslog (D-10), but the algorithm itself is small enough to inline using the engine's existing entity bookkeeping.

**Two paths inside FriendlyPlayerExporter** (verified by reading `.venv/lib/python3.12/site-packages/hslog/export.py:334-386`):

1. **AI heuristic (fast path):** During `CREATE_GAME`, if exactly one player has `lo == 0` (AI) and one has `lo != 0` (real account), the real account is friendly. Resolves immediately on CREATE_GAME consumption.
2. **First-SHOW_ENTITY-in-HAND fallback (slow path):** Watch CONTROLLER tags during FULL_ENTITY/SHOW_ENTITY/TAG_CHANGE. The first SHOW_ENTITY whose target zone is HAND is the friendly player's first revealed mulligan card → that entity's controller is the friendly player_id.

**When to use:** AI heuristic resolves at CREATE_GAME for solo / casual-vs-AI. Multiplayer (both `lo != 0`) requires the SHOW_ENTITY fallback, which means `_friendly_player_id` may briefly be `None` between CREATE_GAME and the first mulligan reveal. Planner decision: either default to `1` until resolved (current behavior), OR mark all events emitted before resolution as "controller unknown" and re-emit / patch retrospectively. **Recommendation:** Default to `1`; once the SHOW_ENTITY fallback fires, update `_friendly_player_id` and re-bucket already-recorded `_player_drawn`/`_opponent_drawn` lists. Phase 2's `CardDrawn` event already carries the raw `controller` value (`test_card_drawn_controller_reflects_log_controller` locks this in), so subscribers can re-bucket too if needed.

**Engine wiring (concrete):**
```python
# stonereader/services/_engine.py
def _on_create_game(self, p: CreateGamePacket) -> List[GameEvent]:
    # ... existing reset + record_entity ...
    # WR-02 fix: AI heuristic
    ai_players = [pid for (eid, name, hi, lo) in p.players for pid in [self._entities[eid].get("PLAYER_ID")] if lo == 0]
    real_players = [pid for (eid, name, hi, lo) in p.players for pid in [self._entities[eid].get("PLAYER_ID")] if lo != 0]
    if len(ai_players) == 1 and len(real_players) == 1:
        self._friendly_player_id = real_players[0]
    else:
        self._friendly_player_id = None  # Wait for SHOW_ENTITY fallback
    # ... existing rest ...
```

**Required parser change:** `CreateGamePacket.players` is currently `Tuple[Tuple[int entity_id, str name, int hi, int lo], ...]` — it drops `player_id`. The exporter needs `player_id`. Update `_packets.py` and `_parser.py` to retain `player_id` in the tuple: `(entity_id, player_id, name, hi, lo)`. This is a small breaking change to `CreateGamePacket` that requires updating engine code and the existing engine tests in `tests/test_services/test_engine.py` (which currently call `players=((2, "P1", 1, 1), ...)`). [VERIFIED: hslog Player packet shape is `(ts, entity, player_id, hi, lo)` per `inspect.getsource(hslog.packets.CreateGame.Player.__init__)`.]

### Pattern 5: Auto-Deck-Detection (D-10/D-11, LIVE-08)

**What:** When `state.player_deck` reaches 30 entities (full reveal), compute `Counter(entity.card_id for entity in state.player_deck if entity.card_id)`. **Concrete shape:**

```python
def _run_auto_detection(self, state: GameState) -> None:
    revealed = Counter(e.card_id for e in state.player_deck if e.card_id)
```

### Pattern 7: Global Hotkey Service (D-01, LIVE-09)

**What:** Wrap `wx.Window.RegisterHotKey(hotkey_id, modifiers, virtual_key_code) -> bool` and `UnregisterHotKey(hotkey_id) -> bool`. Bind `wx.EVT_HOTKEY` once on the frame; dispatch to a registered callback by `hotkey_id`.

**Modifier constants (use wx-native, not win32con):** [VERIFIED]
- `wx.MOD_ALT == 1`
- `wx.MOD_CONTROL == 2`
- `wx.MOD_SHIFT == 4`
- `wx.MOD_WIN == 8`
- For `Ctrl+Shift+R`: `wx.MOD_CONTROL | wx.MOD_SHIFT == 6`. (Don't use `wx.ACCEL_CTRL` — that's a different constant for menu accelerators.)

**Virtual-key code:** wxPython accepts `ord("R")` (== 0x52 == VK_R) directly. [VERIFIED: existing `app.py:243` uses `ord("Q")` for menu accel; same pattern works for `RegisterHotKey`.]

**Signature & lifecycle (concrete):**
```python
# stonereader/services/_global_hotkey.py
from __future__ import annotations
import logging
from typing import Callable, Dict, List, Tuple
import wx

logger = logging.getLogger(__name__)


class GlobalHotkeyService:
    """Wraps wx.Frame.RegisterHotKey for system-wide chord registration.

    Application IDs MUST be in 0x0000–0xBFFF per Win32 spec. We use 1000+
    to leave room for caller-supplied IDs and to keep them visually distinct.
    """

    def __init__(self, frame: wx.Frame) -> None:
        self._frame = frame
        self._next_id = 1000
        self._callbacks: Dict[int, Callable[[], None]] = {}
        self._registered: List[Tuple[int, str]] = []  # (id, label) for diagnostics
        self._failed: List[str] = []
        frame.Bind(wx.EVT_HOTKEY, self._on_hotkey)

    def register(
        self, modifiers: int, vk: int, callback: Callable[[], None], label: str = ""
    ) -> bool:
        """Register a global hotkey. Returns True on success.

        On Windows, RegisterHotKey returns False if the chord is already
        registered by another app (ERROR_HOTKEY_ALREADY_REGISTERED, code 1409).
        """
        hkid = self._next_id
        self._next_id += 1
        ok = self._frame.RegisterHotKey(hkid, modifiers, vk)
        if not ok:
            logger.warning(
                "RegisterHotKey failed for %s (mods=0x%x vk=0x%x); skipping",
                label or f"id={hkid}", modifiers, vk,
            )
            self._failed.append(label or f"mod=0x{modifiers:x} vk=0x{vk:x}")
            return False
        self._callbacks[hkid] = callback
        self._registered.append((hkid, label))
        logger.info("Registered global hotkey: %s", label or f"id={hkid}")
        return True

    def clear_all(self) -> None:
        """Unregister every hotkey. Idempotent. Safe to call from frame close."""
        for hkid, _label in self._registered:
            try:
                self._frame.UnregisterHotKey(hkid)
            except Exception:
                logger.exception("UnregisterHotKey failed for id=%d", hkid)
        self._registered.clear()
        self._callbacks.clear()

    @property
    def failed(self) -> List[str]:
        """Labels of hotkeys that failed to register (e.g., already taken)."""
        return list(self._failed)

    def _on_hotkey(self, event: wx.KeyEvent) -> None:
        hkid = event.GetId()
        callback = self._callbacks.get(hkid)
        if callback is None:
            return
        try:
            callback()
        except Exception:
            logger.exception("global hotkey callback raised; ignoring")
```

**Important Win32 details verified:**
- ID space: applications must use 0x0000–0xBFFF. We use 1000+. [CITED: docs.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey]
- Failure mode: returns `BOOL` 0/non-zero. wxPython exposes this as Python `bool`. Default `GetLastError()` on failure is `ERROR_HOTKEY_ALREADY_REGISTERED (0x581 == 1409)` when another app holds the chord. wxPython does NOT expose `GetLastError`, so we treat all `False` returns as "skip and warn" without distinguishing the reason. [CITED: same MSDN page; VERIFIED via wxPython source — `RegisterHotKey -> bool` in `wx.Window.RegisterHotKey` docstring.]
- F12 is reserved for the debugger; never register. Avoid `Ctrl+Alt+Delete` (system-reserved). `MOD_WIN` chords are reserved for the OS. [CITED: same MSDN page]
- `MOD_NOREPEAT` (0x4000): when set, OS does not repeat the hotkey on key-hold. **Recommendation:** OR `MOD_NOREPEAT` (= 0x4000) into the modifier flags so a held chord doesn't fire 30 times per second. wxPython accepts arbitrary integer modifier flags, so `wx.MOD_CONTROL | wx.MOD_SHIFT | 0x4000` works. [CITED: MSDN]

**No NVDA conflict expected for `Ctrl+Shift+<letter>` chords:** [VERIFIED via WebSearch] NVDA's primary modifier is its own Insert/CapsLock key, not Ctrl+Shift. Ctrl is reserved by NVDA only as a "silence speech" gesture (press Ctrl alone). Compound chords like Ctrl+Shift+R are NOT used by NVDA's default keymap. Hearthstone itself uses single-letter shortcuts (no Ctrl prefix) for in-game actions like "ESC = menu", "1-0 = play card from hand". So `Ctrl+Shift+R/O/D` are safe choices. [Source: dequeuniversity.com/screenreaders/nvda-keyboard-shortcuts] [Confidence: MEDIUM — confirmed NVDA doesn't reserve them, but cannot exhaustively verify all third-party Windows utilities the user has installed.]

**Letter assignment (planner picks; recommendations):**
- `Ctrl+Shift+R` — Remaining Deck (browse-open)
- `Ctrl+Shift+O` — Opponent Hand (browse-open)
- `Ctrl+Shift+D` — Deck counts (speak-only LIVE-06)

Avoid letters that map to common Hearthstone in-game shortcuts. Avoid `Ctrl+Shift+S` (system "save" semantics in many apps), `Ctrl+Shift+Q` (some apps use for quit). Avoid `Ctrl+Shift+P` (NVDA "pass next key through" gesture — actually NVDA's pass-through is NVDA+F2, but Ctrl+Shift+P is used by various IDEs/launchers). Avoid `Ctrl+Shift+Esc` (Task Manager — system reserved). [Confidence: MEDIUM]

### Anti-Patterns to Avoid

- **Calling `self._speech.speak` from `_on_game_event`** — violates D-07 (silent during arrow-read). All speech must be initiated by user action (arrow press, hotkey, panel-entry).
- **Mutating `GameState` fields in the presenter** — `GameState` is frozen. Construct new state in the engine; presenter only reads.
- **Holding a strong reference to `tracker._subscribers` content** — subscribe with the bound method, unsubscribe in `cleanup()`. Otherwise a re-instantiated `LiveGamePresenter` (e.g., on hot-reload) leaks the old one.
- **Re-registering hotkeys without unregistering** — Windows replaces the binding silently on Win Server 2003 but leaks IDs on client OSes. Always `UnregisterHotKey` before re-registering.
- **Routing global hotkeys through `InputLayer`** — InputLayer handles `EVT_CHAR_HOOK` for in-app shortcuts. Global hotkeys arrive as `EVT_HOTKEY` (a different message), and `Ctrl/Alt` combos are explicitly skipped by `InputLayer._on_char_hook` (line 84-86). Two separate channels.
- **Using `keyboard`/`pynput` for global hotkeys** — locked rejected by D-01.
- **Building lineage data with the engine still importing hslog directly** — Phase 2 D-10 forbids this. Lineage is computed using engine-internal `_block_subjects` + `_entities` bookkeeping.

## Common Pitfalls

### Pitfall 1: `_friendly_player_id` resolution is asynchronous in multiplayer
**What goes wrong:** The AI-heuristic path resolves at CREATE_GAME, but the SHOW_ENTITY-fallback path may not resolve until several events later (mulligan reveal). Events emitted before resolution will have `controller` correctly set (raw tag pass-through is locked), but the engine's internal `_player_drawn`/`_opponent_drawn` lists will have bucketed cards based on the default `_friendly_player_id = 1`. If the local player turns out to be Player 2, those lists are inverted.
**Why it happens:** `_handle_zone_change` decides bucketing by comparing `controller == self._friendly_player_id` at the moment the event fires. If `_friendly_player_id` is wrong at that moment, the wrong bucket gets the row.
**How to avoid:** When the SHOW_ENTITY fallback finally resolves the friendly player, the engine must re-bucket any prior drawn rows. Concretely: if `_friendly_player_id` changes from 1 to 2, swap `_player_drawn` and `_opponent_drawn`, and re-emit a single sentinel event subscribers can use to refresh state. Alternatively (simpler): defer bucketing until `_friendly_player_id` is known — buffer rows until that moment. Pick one consistent path.
**Warning signs:** A test where `_friendly_player_id` is initially `None` then resolved to `2` shows `state.player_drawn` containing the opponent's cards.

### Pitfall 2: `wx.CallAfter` ordering of "show panel + jump zone"
**What goes wrong:** `nav.show_panel("Live Game")` schedules `wx.CallAfter(focus_target.SetFocus)`. If the browse-open hotkey callback then immediately calls `presenter.jump_to_zone("remaining_deck")`, the speech might fire before the panel is visible (focus isn't yet on the panel, screen reader reads the *previous* panel's title).
**Why it happens:** `show_panel` schedules focus async via `wx.CallAfter`; subsequent code in the same callback runs synchronously and may speak before focus moves.
**How to avoid:** Wrap the zone-jump in another `wx.CallAfter` so it runs after the focus event, OR (better) have `presenter.jump_to_zone` just call `navigate_to_zone` directly (existing `ZoneNavigationMixin` method). The speech firing slightly before focus arrival is benign — NVDA doesn't care about focus to read announced text.
**Warning signs:** Manual test: press `Ctrl+Shift+R` from Hearthstone — the Remaining Deck zone-entry speech is heard, but arrow keys initially do nothing because focus hasn't reached the panel yet.

### Pitfall 3: Live-update event handler runs while user is mid-arrow
**What goes wrong:** User arrow-keys through the Remaining Deck zone; mid-arrow, a `CardDrawn` event fires; presenter calls `_notify_view()` which triggers a panel re-render; the underlying ListCtrl gets `SetItems`-ed and the cursor jumps to row 0; the user's next arrow key reads the wrong row.
**Why it happens:** wx ListCtrls don't preserve selection across `SetItems` unless explicitly told. The presenter's `_zone_cursors` integer cursor is the source of truth and should not be touched by `_notify_view`, but the *view's* visible selection is a separate state.
**How to avoid:** After `_notify_view` re-renders, the view should re-select the row at `presenter._zone_cursors[current_zone]` (or the row whose logical key matches the previous cursor's key). This is a view-layer concern — pass cursor info into the view's render method.
**Warning signs:** Test: simulate cursor=5, fire a CardDrawn event, then call `move_in_zone(1)` — the speech should announce the row at cursor=6 of the (possibly shrunken) list, not row 1.

### Pitfall 4: `RegisterHotKey` silently held by another app on launch
**What goes wrong:** User has Spotify running, which holds `Ctrl+Shift+P` for play/pause. StoneReader's `RegisterHotKey` for `Ctrl+Shift+P` returns `False`. If the app silently swallows this, the user wonders why their hotkey doesn't work.
**Why it happens:** `RegisterHotKey` returns `bool`; wxPython doesn't expose `GetLastError`. Per "Claude's Discretion" in CONTEXT.md, we log + speak the failure list. Without that announcement, the failure is invisible.
**How to avoid:** Aggregate failures in `GlobalHotkeyService._failed`. After registration, if any failed, speak a one-time announcement at startup: `"Could not register hotkeys: Remaining Deck, Opponent Hand."` Don't crash; the panel is still reachable from Home menu.
**Warning signs:** Manual test: launch the app while another app holds `Ctrl+Shift+R` (e.g., temporarily register it via PowerShell `Register-Hotkey`), confirm StoneReader announces the failure.

### Pitfall 5: Repeat-fire while chord is held
**What goes wrong:** User holds `Ctrl+Shift+R` for half a second; Windows fires `WM_HOTKEY` 30 times; speech queue floods.
**Why it happens:** Default `RegisterHotKey` behavior repeats the message at the OS keyboard repeat rate.
**How to avoid:** OR `MOD_NOREPEAT` (0x4000) into the modifier flags. wxPython accepts arbitrary modifier values. [CITED: MSDN docs say MOD_NOREPEAT changes hotkey behavior so keyboard auto-repeat does not yield multiple notifications.]
**Warning signs:** Manual test: hold `Ctrl+Shift+R`; without MOD_NOREPEAT, NVDA stutters; with it, the chord fires once and silence resumes.

### Pitfall 6: Detected deck name persists across games
**What goes wrong:** Player A's deck is detected as "Reno Quest Mage". Player A queues another game with a different deck. The presenter still shows "Reno Quest Mage" because `_detected_deck_name` was never cleared.
**Why it happens:** `_run_auto_detection` is gated by `_detection_attempted`, which is reset at `GameStarted` per the snippet above. **However**, between games (after `GameEnded` and before `GameStarted`), the player can open the panel and see stale state. Per D-08, that's intended ("preserve last game on GameEnded"). But the next `GameStarted` MUST reset both `_detected_deck_name` and `_detection_attempted`.
**How to avoid:** Set `self._detected_deck_name = None` and `self._detection_attempted = False` inside the `GameStarted` branch of `_on_game_event`. Verify via test: simulate two consecutive games; assert detection runs twice, possibly with different results.
**Warning signs:** Test that runs two `GameStarted` events back-to-back and asserts `_detection_attempted` is `False` after the second one (until detection completes).

### Pitfall 7: Lineage tracking across reconnect
**What goes wrong:** Player reconnects mid-game; Hearthstone re-emits the full game state as a new CREATE_GAME (Phase 2 doc line 139). The engine resets per `_on_create_game`. Lineage data accumulated before the reconnect is lost; opponent-hand entities arrive as plain FULL_ENTITY without surrounding generator BLOCK_START.
**Why it happens:** Reconnection rebuilds state without replaying the original BLOCK_STARTs. Lineage is therefore unrecoverable for any opponent-hand card that was generated before the reconnect.
**How to avoid:** Document the limitation. After a reconnect, opponent-hand rows show "drawn turn N" without lineage even if originally generated. This matches HDT/Firestone behavior (also locked by reality of the log format). Test: feed `tests/fixtures/log/reconnect.log` and assert lineage is missing/empty for all opponent-hand entities created in the second CREATE_GAME block.
**Warning signs:** A reconnect-then-query test that expects lineage; planner/implementer should know the test's expectation is "no lineage" not "preserved lineage".

### Pitfall 8: Auto-detection misfires on partial-deck states
**What goes wrong:** Detection runs at `len(state.player_deck) == 30`, but if Hearthstone reveals only 28 cards initially (some game modes don't reveal all 30 — Battlegrounds, Twist), the threshold never trips.
**Why it happens:** Constructed Standard/Wild/Classic always reveals 30. Other modes may not. Phase 3 is scope-limited to standard play (D-08 implies single-game).
**How to avoid:** If `state.game_type` indicates non-constructed (BATTLEGROUNDS, ARENA, etc.), skip detection ("Detection unavailable for this game mode"). Standard match: 30 cards is the always-true invariant.
**Warning signs:** Battlegrounds fixture (Phase 2 D-17 mentions one — verify it exists by listing `tests/fixtures/log/`) — if present, test that detection is skipped.

[Note: `tests/fixtures/log/` contains 4 fixtures: `match_start.log`, `mid_game.log`, `game_end.log`, `reconnect.log` — VERIFIED via `ls`. No Battlegrounds fixture; Phase 2 D-17 originally aspired to capture one but Phase 2 capture only landed Constructed games. Acceptable for Phase 3 since the v1 scope targets Constructed.]

```python
# stonereader/presenters/live_game.py
def jump_to_zone(self, zone_name: str) -> None:
    """Public entry point used by global hotkeys (browse-open) and home menu."""
    label_map = {
        "remaining_deck": "Remaining deck zone",
        "opponent_hand": "Opponent hand zone",
        "opponent_played": "Opponent played zone",
    }
    label = label_map.get(zone_name, zone_name)
    items = self.get_zone_items(zone_name)
    if not items:
        self._speech.speak(f"{label}: empty")
        return
    # D-17: "Zone name, N of M cards. <first row read>."
    cursor = self._zone_cursors.get(zone_name, 0)
    cursor = max(0, min(cursor, len(items) - 1))
    self._zone_cursors[zone_name] = cursor
    self._current_zone = zone_name
    first_row = self._format_item_speech(items[cursor], cursor + 1, len(items))
    # Strip the "x of y" suffix that _format_item_speech adds because we
    # speak it differently in the entry format.
    self._speech.speak(f"{label}, {len(items)} cards. {first_row}")
```

## Open Questions (RESOLVED)

1. **Should the SHOW_ENTITY fallback path for `_friendly_player_id` re-bucket already-recorded events?**
   - **RESOLVED:** Re-bucket from authoritative entity state (not blind list-swap).    - What we know: AI-heuristic resolves at CREATE_GAME; SHOW_ENTITY fallback may resolve later.
   - What's unclear: Whether to delay event emission until resolution OR re-bucket on resolution. Both have correctness costs.

### Known Threat Patterns for Python desktop + wxPython + Power.log

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malformed log line crashes parser | Denial-of-Service | hslog catches `ParsingError`/`RegexParsingError` already (Phase 2 `_parser.py:64-79`); engine `apply()` per-packet try/except (`_engine.py:127`). Phase 3 inherits both. |
| Crafted log line tricks engine into wrong friendly_player attribution | Spoofing (within local app) | FriendlyPlayerExporter algorithm is deterministic over packet stream. A user maliciously editing Power.log could fool it, but they'd be deceiving themselves. Not a real threat. |
| Stale OS hotkey registration leaks across crashes | Resource leak | `MainWindow._on_close` calls `clear_all()` before `Destroy()`. Crash without close: process exit cleans up the hotkey table. Acceptable failure mode. |
| Deckstring in `decks` table is malformed (Phase 1 corruption) | Data integrity | Auto-detection wraps `parse_deckstring` in try/except; malformed deckstrings are skipped from the match candidate list. |
