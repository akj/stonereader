# Phase 3: Live Game Tracking - Context

**Gathered:** 2026-04-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Connect Phase 2's headless `GameTracker` (subscriber bus + frozen `GameState` snapshots + typed events) to user-facing speech announcements and a navigable in-app surface, so screen reader users can query live game state — primarily *remaining* deck composition and opponent hand inspection — via global hotkeys (`wx.Frame.RegisterHotKey`) while Hearthstone has focus.

**Scope discipline:** Hearthstone Access (the in-game accessibility mod) already covers your hand contents, mana for both players, board state, and a recent-action replay. Phase 3 explicitly targets the gaps HA does NOT cover. Anything HA already handles is out of scope for v1 hotkeys.

**Phase 3 also fixes WR-02** (friendly_player_id stub in `_engine.py`) — explicitly called out in PROJECT.md as a Phase 3 prerequisite. Without this, LIVE-02/03/04 are inverted in ~50% of games.

</domain>

<decisions>
## Implementation Decisions

### Global Hotkeys (LIVE-09)

- **D-01:** **Hybrid model with shared-modifier namespace.** A small set of global chords using the same `Ctrl+Shift+<letter>` modifier prefix (the de facto leader namespace). True Vim-style leader keys are rejected — under Windows `RegisterHotKey`, the OS routes only the specific registered chord; subsequent keys go to whoever has focus (Hearthstone). The known-working leader alternatives all have real costs (focus theft, dynamic re-registration races, low-level keyboard hooks that conflict with NVDA/JAWS). Sharing a modifier prefix gives the same mental "leader" feel without any of those costs.
- **D-02:** **Hotkey query gaps targeted in v1:** (1) **Remaining deck composition** — what cards are still in your deck and how many of each (browse-open: hotkey opens the Live Game panel zoomed to the remaining-deck zone). (2) **Opponent hand inspection** — per-card metadata (browse-open: opens panel zoomed to opponent-hand zone). HA already handles own-hand, both-mana, board, recent-replay — these get no v1 hotkey.
- **D-03:** **Two query types: speak-only and browse-open.**
  - **Browse-open** (always opens the Live Game panel + jumps cursor to a target zone): Remaining Deck panel, Opponent Hand panel.
  - **Speak-only** (just announces via SpeechService; no UI surface change): exact list deferred to planner — likely candidates include LIVE-06 deck-count comparison ("18 left, opponent 22"). Format is locked (D-12) so any added hotkey speaks consistently.
- **D-04:** **Opponent hand v1 detail level: position + identity (or `?`) + drawn turn + creation lineage.** Lineage = "generated by Cabal Shadow Priest" / "discovered from Wand of Disintegration". Requires Phase 3 engine extension to link `FullEntityPacket` to its creating `BlockStartPacket` (engine bookkeeping pass). Discover-in-progress signal (mid-Discover state) deferred to v2.

### Live Game Panel Structure

- **D-05:** **Three zones in the Live Game panel:** (1) Remaining Deck, (2) Opponent Hand, (3) Opponent Played History. Each zone uses `ZoneNavigationMixin` with cursor + N-of-M speech + down-arrow detail inspection (same pattern as `CardBrowserPresenter`). NO separate "status" zone — matchup ("Mage vs Warrior") and detected deck name go in the panel title bar.
- **D-06:** **One UI surface, two ways in.** The Live Game panel is reachable from the home menu (add `"Live Game"` to `MENU_ITEMS` in `presenters/home.py`) AND directly via global hotkeys (browse-open hotkey calls `nav.show_panel("Live Game")` then jumps cursor to the targeted zone). HTML/WebView popup explicitly rejected — for NVDA users it's a context switch between app SR mode and browser SR mode, plus significant new architecture (state bridge, parallel a11y stack) for zero SR benefit.
- **D-07:** **Live-update on relevant `GameEvent` subscriptions, with cursor preservation.** Panel re-renders when Phase 2 events affect a visible zone (e.g. `CardDrawn` → recompute remaining deck; `CardPlayed`/`CardRevealed` → update opponent_played and opponent_hand). Cursor stays on the same logical card if possible (e.g., "Reno Jackson" stays selected even if list reorders). Updates are silent during arrow-read (no announcement) — user explicitly arrows to hear changes. This keeps speech from fighting with NVDA's own arrow read.
- **D-08:** **Lifecycle:** Auto-reset on `GameStarted` (panel clears to fresh state, title updates to new matchup, all zones empty until events flow in). Preserve last game on `GameEnded` (post-game review). New `GameStarted` overwrites the preserved state. When no game has been seen this session: panel shows "No game in progress" across all zones.
- **D-09:** **Silent on lifecycle.** No speech at `GameStarted` or `GameEnded`. No automatic panel-open on `GameStarted`. User explicitly queries via global hotkey or opens the panel via home menu. Most non-invasive; preserves Hearthstone focus during gameplay.

### Auto-Deck-Detection (LIVE-08)

- **D-10:** **Detect once per game using the full revealed deck list.** Detection fires after the engine has fully consumed `CreateGamePacket` and `GameState.player_deck` is populated with the 30 cards Hearthstone reveals to the local player at game start. This is well-established behavior used by HDT and Firestone (verified via web research and `docs/superpowers/research/2026-04-08-powerlog-parsing.md` line 35 reference to hslog's `FriendlyPlayerExporter`). Result is cached on the `LiveGamePresenter` for the duration of the game; subsequent panel queries / hotkeys see the same detected deck. Re-runs on next `GameStarted`.
- **D-11:** **Strict exact match: one match wins, otherwise no match.** Compute multiset of `(card_id, count)` over the 30 revealed cards. For each saved deck in the SQLite `decks` table, compare to its multiset. If exactly one saved deck matches exactly → that's the detected deck (panel title shows its name). If 0 or 2+ match → "Unknown deck" in the panel title. Strict matching keeps the panel honest about uncertainty; a "best-fit" approach risks silent mis-attribution.
- **D-12:** **Remaining-deck calculation always uses the in-game `player_deck`** (revealed by Hearthstone via `CREATE_GAME` and decremented on draw events), regardless of detection result. The detected saved deck name is only metadata for the panel title. This means the Remaining Deck zone works for unsaved decks too (Hearthstone Wild experiments, friend's borrowed decks).

### Speech Format

- **D-13:** **Per-row format for Remaining Deck zone:** `"Reno Jackson, 1 copy"` / `"Fireball, 2 copies"`. Sorted by mana cost ascending then alphabetically (matches HDT/Firestone overlay convention). Cards drawn-to-zero stay listed as `"0 copies"` so user can confirm they came out. Down-arrow reveals card text (cost, attack/health, card text — reuses `Card.detail_lines()`).
- **D-14:** **Per-row format for Opponent Hand zone (compact contextual):** `"Position 3, Reno Jackson, drawn turn 5"` (revealed) or `"Position 3, unknown, generated by Wand turn 5"` (lineage known) or `"Position 3, unknown, drawn turn 5"` (no lineage). Down-arrow reveals card text + full lineage chain.
- **D-15:** **Per-row format for Opponent Played zone:** `"Turn 6, Reno Jackson"`. Chronological (most recent at top OR bottom — planner's call; matches whatever direction `ZoneNavigationMixin` already uses for "newest" semantics in DeckManager). Down-arrow reveals card text.
- **D-16:** **Speak-only global hotkey format (single-fact, while Hearthstone has focus): tight one-sentence.** Examples: `"18 left, opponent 22."` / `"Opponent has Reno Jackson, drawn turn 5, generated by Wand."`. Short enough that NVDA finishes before the next Hearthstone action. Don't fight gameplay.
- **D-17:** **Panel-entry / hotkey-jump speech:** `"Remaining deck zone, 18 of 18 cards. 1 mana, Glacial Shard, 1 copy."` Format = zone name + count + first-row read. Tells user where they landed, total count, and the first row, so they can immediately arrow without re-orienting. Matches `CardBrowserPresenter` zone-entry pattern.

### WR-02 — Friendly Player Resolution

- **D-18:** **Use hslog's `FriendlyPlayerExporter` to resolve the local player per-game.** Wire it into the engine's CREATE_GAME flow so `_friendly_player_id` is set correctly each game (could change between games if user logs into different accounts). Zero new dependencies (hslog is already in via Phase 2 D-09). Matches HDT/HSReplay exactly. Replaces the stub at `stonereader/services/_engine.py` line ~85. The baseline test `test_card_drawn_controller_reflects_log_controller` (already added in Phase 2) locks the raw-controller pass-through; new tests should cover both Player-1-is-local and Player-2-is-local cases via captured fixtures (D-17 from Phase 2). Without this fix, LIVE-02/03/04 (remaining deck, drawn-this-game, opponent played) are inverted in ~50% of games.

### Engine Extensions Required by Phase 3

- **D-19:** **Engine extension 1 — creation lineage tracking** (supports D-04 opponent hand creation lineage). When a `BlockStartPacket` opens a `POWER` block whose subject is a known card (e.g., Cabal Shadow Priest, Wand of Disintegration's Discover trigger), and a `FullEntityPacket` arrives inside that block whose entity ends up in the opponent's hand, record `(opponent_entity_id → "generated by <subject_card_name>")` on the entity. Stored in `GameEntity.tags` or as a new optional field — planner picks. Discover-in-progress (mid-block) NOT tracked in v1.
- **D-20:** **Engine extension 2 — sorted remaining-deck view** (supports D-13). Engine already has `player_deck: Tuple[GameEntity, ...]` (Phase 2 D-08). Phase 3 needs either (a) a derived computed property on `GameState` that returns sorted-by-cost-then-name `(Card, count)` tuples, OR (b) presenter-side sorting/grouping. Planner's call. Either way, no mutation of frozen state.

### Claude's Discretion

- Exact letter assignments for global hotkeys (e.g., `Ctrl+Shift+R` for Remaining Deck, `Ctrl+Shift+O` for Opponent Hand) — planner picks letters that don't collide with Windows or NVDA conventions.
- Conflict / failure handling when `RegisterHotKey` fails (key already bound by another app) — log + speak the error; skip that hotkey. Planner finalizes UX.
- Diminishing-verbosity on repeat hotkey presses (QOL-02 is v2; v1 may use simple repeat).
- Speak-only hotkey lineup (D-03) — likely LIVE-06 deck-count comparison; planner decides which LIVE-* requirements naturally fall out of the panel zones vs need their own hotkey.
- Internal naming for the Live Game panel/presenter file (`live_game.py` recommended for parity with `card_browser.py`, `deck_manager.py`).
- Whether the global hotkey service is one new module (`stonereader/services/_global_hotkey.py` — matches Phase 2 underscore convention) or sits in the presenter layer — planner's architectural call.
- Lineage-tracking storage shape inside the engine (D-19) — extra dict, new field on `GameEntity`, or `tags` — planner picks.
- Sort/group implementation location for D-20 — `GameState` computed view vs `LiveGamePresenter` sort — planner picks.

### Constraint Notes

<specifics>
## Specific Ideas

- **HA-driven scope discipline:** Hearthstone Access already speaks own-hand, both-mana, board, recent-action replay. StoneReader's value is in the *gaps* — primarily remaining deck composition and opponent hand inspection with creation lineage. Resist the urge to duplicate HA functionality; if a hotkey would just repeat what HA says, drop it.
- **Match HDT/Firestone behavioral defaults where they agree.** Auto-detection from CREATE_GAME deck list (D-10) and `FriendlyPlayerExporter`-based local-player resolution (D-18) both come from HDT. Sorted-by-cost-then-name remaining deck (D-13) matches HDT/Firestone overlays.
- **Speech format = "tight one-sentence" for hotkeys, "name + count" for deck rows, "position + identity + drawn turn" for opponent-hand rows.** Down-arrow always reveals more detail. Don't fight gameplay reaction time with verbose speech.
- **Lineage tracking is the most novel engine work in Phase 3.** D-19 requires the engine to remember which `BlockStartPacket` was open when a `FullEntityPacket` arrived for an opponent-hand entity, and look up the block's subject card name. Planner should prototype this against captured fixtures (Phase 2 D-17) before committing to a final API shape.

</specifics>
